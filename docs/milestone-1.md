## 二、三条被推翻的判断（这是本阶段最大的收获）

### ① 「插画深度能给出体积感」→ 实际只有「剪影」

7 张输入实测：真人照片能恢复真实结构；厚涂/平涂人物都是**一块等深度的板**（主体内 IQR 仅占全幅 0.7~4.3%）；黑白漫画几乎无分层。

**后果**：点云模式拿不到线稿，因为它不在深度里。这条不可优化。

### ② 「真实点云不规则，所以不会有摩尔纹」→ 反投影恰恰是**严格规则网格**

我和 web-render **各自独立**说过这句话，都错了。深度图逐像素反投影 = 规整网格，位置哈希抽稀必然产生条带。
**教训：「真实数据」不等于「不规则数据」。反投影出来的点云比任何合成点云都规则。**

### ③ 「点云模式的主次颠倒，根因是墨量按亮度」→ **主因是深度方向反了**

### ④（附）「点云模式只能做小幅视差配角」→ 该判断建立在错误地基上，已被作者收回

## 三、那个地基级 bug

```
单目深度 d 是距离，越大越远（实测：主体 d≈0.48 / 背景 d≈0.86）
反投影写的是 z = d（正值）
相机按「+z 朝观察者」放在 +Z 朝 -Z 看
→ 叠加后：背景离相机更近、主体更远
```

**一行符号错误，污染了三条判断**，而当时都被当成「点云模式天生不行」：

| 症状 | 真实原因 |
|---|---|
| 空气透视把主体洗白 | 雾加在了"近景"上，而那个"近景"其实是背景 |
| 按深度上墨落到背景 | 同理 |
| 视差方向相反 | 背景比主体动得多 |

**为什么没早发现**：当时靠"看渲染图好不好看"验证——而"好看"没有基准，所以反了也看不出来。

**怎么抓到的**：用画面半径 `rho` 分区量 z，发现主体 z 比背景小 → 与"主体应该近"矛盾。

**最终约定**（`docs/selection.md §4.4`）：`z = -d`，相机在 `+Z` 朝 `-Z`。在 Go 侧翻而非渲染层翻，理由是数据本身要符合文档、且 PLY 导出给外部工具时方向才对。

**纪律**：两边只能有一边翻。四步串行推进，中间"两边都翻"的窗口是危险的。

## 四、踩过的坑（12 个，分四类）

### 环境类（4）

| 坑 | 教训 |
|---|---|
| `PIP_REQUIRE_VIRTUALENV` 与 conda 不兼容 | pip 只认 venv；conda 里 `sys.prefix == sys.base_prefix`。硬闸要选在真正能生效的层 |
| **只重定向 pip cache 不够，`TEMP` 才是大头** | 2.4 GB torch 轮子解到 C 盘，**C 盘 3.8 → 1.11 GB**。"所有缓存落 E 盘"要数清 cache/temp/home/hub 四条路径 |
| `evo` 是硬 import 但单图用不到 | 第二处懒加载补丁；`plyfile` 要求 numpy>=2 与 DA3 冲突，卸载 |
| PS 5.1 写 UTF-8 带 BOM 会毁 Python 源码 | 用 .NET 无 BOM 写入；提交信息用 `git commit -F` 避免中文双引号被拆 |

### 契约类（3）

- 响应帧也带 4 字节长度前缀（`total_len + status + body`）
- 相机约定三端必须一致（`+x` 右 / `+y` 上 / `+z` 朝观察者）
- Vue/框架无关：`go:embed` 不能跨包 → 用 `-web-dist` 从磁盘服务

### 假设类（5）——全是「为 fixture 写的假设」

| 假设 | 换真实数据后的后果 |
|---|---|
| `FRAME_MARGIN=0.9` 故意裁边 | 裁掉 10% 画面 |
| 包围盒套框 | 「主体板+背景板」时盒角是空的，算太近 |
| 位置哈希抽稀 | 规则网格 → 条带摩尔纹 |
| 墨量按绝对亮度 | 浅色主体消失、背景抢戏 |
| 仰角钳制 ±(4°,88.6°) | 正面基准极角 90°，把摆动压成单边 |

**规律：每次换数据都会暴露一批隐式假设。这不是 bug，是测试数据在起作用。**

### 地基级（1）
z 符号（见上一节）。

## 五、验证方法学（本阶段最值得带走的东西）

这台机器上 **Playwright 不可用**（没装 Chrome），所以视觉验证大量依赖间接证据。反而逼出了一套更硬的方法：

| 方法 | 用在哪 | 效果 |
|---|---|---|
| **数值优先于看图** | 深度质量、z 符号、采样富集 | 抓到了肉眼看不出的错误 |
| **同字节对照（只翻一个变量）** | z 符号等价性 | 证明"必须只翻一边" |
| **SHA-256 首末帧比对** | 无缝循环 | 比"看起来无缝"硬 |
| **独立复算**（`compare-ilcl.py` 把点投回源图算梯度） | 结构采样 | 不依赖渲染层，富集 2.4× |
| **拼版图省成本** | 7 张插画判读 | 一次读图代替 7 次 |
| **先验证测量环境可信** | 重启服务确认构建是新的 | 差点让整个 A/B 白做 |
| **失败时先怀疑度量** | 我误判"结构采样没生效" | 实际是我的梯度归一化写坏了 + 读到正在重生成的文件 |

最后一条的教训：**如果我当时直接说"你的实现没生效"，会浪费队友一整轮。**

## 六、产品结论（已定）

### 三层选项模型

```
第一层：要不要立体？
   图像模式（默认）—— 不碰深度，信息量 100%
   点云模式       —— 依赖深度，信息量 1.24%
第二层：这幅画该怎么读？
   墨量映射（亮度 / 结构 / 深度）+ 主体极性
第三层：画风口味
   5 套预设（应收敛，不要再加）
```

### 两种模式的定位

| 模式 | 定位 |
|---|---|
| **图像模式** | **产品的答案**——"这幅画到底长什么样" |
| **点云模式** | **能动的版画剪影**——有真正的视差与深度分层，但不还原线稿 |

### 关键数字

- 点数/原图像素 ≈ **(process_res / 原图长边)²**；4000px 图在 504/20万档只有 **1.24%**
- 显存：像素 ×7.1（504→1344），显存只 ×1.8（2160→3919 MiB）
- 点数 20/40/60 万：**全部 144 fps**，帧率不是约束
- 结构采样已**打满天花板**：强边缘像素 39,821 个 @775 网格，`edgePointRatio 0.1975 ≈ 19.9%` 上限
- 提档的唯一代价是「背景变密 → 更像点云照片、更不像版画」

## 七、未完成（按原因分类）

### 卡在「L1 基元只有一种」

渲染规格里列了 5 种基元，只实现了**软边圆片**。后果：

| 未做的 | 卡在哪 |
|---|---|
| 油画预设 | 需笔触 quad 基元 |
| 像素立体书预设 | 需 voxel / InstancedMesh |
| 梦境星空预设 | 需粒子 + 加法混合 |
| 笔触跟随（L3） | 同上 |
| bloom / 景深 / 色调映射（L4） | 未排期 |

**所以「更多风格」的第一优先级不是加 shader，是加 quad/InstancedMesh 基元。**

### 完全没开始

- **GIF 编码**（Go 侧 `internal/exporters` 是空的）
- **PLY 导出**（同上）
- 多层 2.5D 视差（kron draft）
- 自定义预设保存（`localStorage` 存几组）

### 已知但可接受

- 面板参数区内部滚动 102px
- 端到端逐字节确定性（GPU 推理非确定性，点数/深度微抖）
- webp/avif 上传不支持（Go 标准库限制）
- 图像模式只有 contain 摆放

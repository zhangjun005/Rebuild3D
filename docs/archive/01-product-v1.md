# 01 · 产品定义 v1

> 状态：待确认
> 约束：单机、8GB 显存、无云、Go 为主语言

---

## 一句话

**丢进 3~6 张房间照片 → 十几秒内出一个有米制尺度、能在浏览器里走进去的 3D 场景 → 框选就能删点、挪东西、量尺寸 → 导出 GLB。**

形态是**本地单机工具**，不是 SaaS。`go run ./cmd/room3d` 起本地服务，浏览器打开，无账号、无云、无上传。

---

## 为什么是"这个"

从调研收敛出来的四条判断：

| 判断 | 依据 |
|---|---|
| 单图点云没有做头 | 它是伪 3D：不精确（不能量）、不完整（背面没有）、不能交付（不是网格/材质/单位） |
| 多视图是分水岭 | DA3 一次前向出 `depth + conf + K + E`，位姿和内参都不用手工猜。"拍几张拼一个房间"从研究课题变成调 API |
| 缺了米制就没有决策价值 | "能不能放下这张沙发"要的是米，不是好看的深度图。`DA3METRIC-LARGE` 是 Apache-2.0，白捡 |
| 编辑是最后一公里 | SuperSplat（MIT，仍在活跃开发）证明浏览器端编辑可行，而且**已把编辑抽象成"可序列化命令流"** |

反面判断同样重要：
- **不做单图重建**（伪 3D）
- **不做量房/测量级工具**（打不过 iPhone Pro 的 LiDAR，也打不过 Canvas/Polycam）
- **不做 image→3D 家具资产**（TRELLIS 官方要 ≥16GB 且只测过 Linux；Hunyuan3D 2.1 全流程 ~29GB）

---

## 用户与场景

v1 只服务**一个人**：会用命令行、想快速把空间变成可交互 3D 的自己/同类人。不做注册、不做权限、不做多人。

三个具体场景（够用就行）：

1. **给自己家建一个可逛的 3D 记忆体** —— 装修前留档、搬家前记录
2. **给一个空间做"体量研究"** —— 这个柜子放这儿会不会压抑？走近看看
3. **给一段素材做参考采集** —— 拍一圈，导出 GLB 丢进 Blender/UE 当体积参考

## 主链路

```
多张照片（3~6 张，手机随手拍，不需要标定）
        │
        ▼  DA3 sidecar（Python，模型常驻，只做推理）
depth[] + conf[] + K[] + E[]
        │
        ▼  Go（产品层，单二进制）
反投影 → 置信度过滤 → 体素下采样 → 空间索引
        │                              │
        ▼                              ▼
浏览器 three.js 查看           编辑命令日志（只存命令，不存改后的点云）
（保留原有第一人称漫游）              │
        │                              ▼
        └──────────────────────► 导出 GLB / PLY
```

**关键结构**：Python 只是一个约 300 行的推理壳，不碰几何、不碰存储、不碰 HTTP 业务。Go 侧是唯一的产品二进制。换 DA3 → DA4 时只换 shell，协议不变。

## 功能范围

### v1 做

| # | 功能 | 说明 |
|---|---|---|
| 1 | 多图上传（1~8 张） | 拖拽，自动按 EXIF 纠正方向 |
| 2 | 多视图重建 | DA3 单次前向 |
| 3 | 米制尺度 | 默认 `DA3METRIC-LARGE`（Apache-2.0） |
| 4 | 置信度过滤 | 用 `conf` 分位数，取代旧代码写死的 `0.1 < d < 50` |
| 5 | 点云生成 + 体素下采样 | Go 侧 numpy-free 实现 |
| 6 | 浏览器查看 | 复用旧项目的 `PointCloudViewer`（含 WASDQE 第一人称漫游） |
| 7 | 编辑：框选/球选删除 | |
| 8 | 编辑：变换选中块（移动/旋转/缩放） | |
| 9 | 编辑：裁剪盒 | 去掉墙外噪点 |
| 10 | 编辑：测量（两点距离 / 包围盒 / 地面高度） | |
| 11 | 撤销 / 重做 | 命令日志重放，天然获得 |
| 12 | 导出 GLB / PLY | GLB 是最大公约数，能被别的工具接手 |
| 13 | 深度图 + 置信度预览 | 让人能看出重建哪里不可靠 |

### v1 不做

| 不做 | 原因 |
|---|---|
| 图像修复 / 物体移除 / 物体插入 | 2D 编辑，不增加几何信息，跟 3D 无关 |
| 文本掩码（GroundingDINO / SAM） | 显存重，且属于"修图"那条线 |
| image→3D 家具资产生成 | 8GB 跑不动（见上） |
| 语义分割 / 点选选中物体 | 需要 SAM 系模型，v2 再说 |
| 3DGS 渲染 | GS head 只在 GIANT 系列（CC BY-NC 非商用，1.15B 装不进 8GB） |
| 点云转 mesh | 需要 Poisson/TSDF，属于"额外一个模型"，v2 再说 |
| 多用户 / 云 / 账号 | 本地单机 |
| 移动端 App | 浏览器够 |

## 交付物

**GLB 是 v1 的核心交付物**，不是点云。

理由：点云几乎没人要——设计师要 CAD，电商要带材质的网格，游戏引擎要 glTF。GLB 至少能被 Blender、UE、three.js 直接吃。先让产物"有人能接住"，再谈质量。

次要交付：`PLY`（点云原始数据）、`SVG/DXF`（v2 的平面图，见 [02](02-direction-expansion.md)）。

## 验收指标

这三条就是"重构能获得什么思考"的具体形态。任何一条挂了，两周内就知道，而不是搭三个月发现方向不对。

| 指标 | 目标 | 挂了说明什么 |
|---|---|---|
| 6 张图端到端耗时 | **< 30 秒** | DA3 在你的硬件上不可用，得降档或减少视图 |
| 房间尺寸误差 | **< 5%**（对比卷尺） | 米制这条路走不通，退回到"观感级" |
| 从拍到能删掉画面里的人 | **< 2 分钟** | 编辑链路设计失败，太重了 |

附加观察项（不设 hard gate）：
- 峰值显存（`torch.cuda.max_memory_allocated()`）—— 目标 < 6GB
- 单次重建的点云点数 —— 目标 10 万~50 万，能在浏览器里 60fps

## 形态与部署

```
Rebuild3D/
  cmd/room3d/          Go 入口（单二进制）
  internal/
    api/               chi 路由 + SSE
    geometry/          反投影 / 体素 / 离群 / rtree
    format/            PLY 读写 / GLB 导出
    edit/              命令定义 + 日志 + 重放
    sidecar/           调 Python 推理进程的客户端
  sidecar/             Python，≈300 行，gRPC 或 msgpack
  web/                 React + three.js（复用旧项目 viewer）
  docs/                本目录
```

启动：
```
go run ./cmd/room3d        # 或 build 出的单二进制
# 自动拉起 sidecar，打开 http://127.0.0.1:8xxx
```

## 与旧项目的关系

旧工程 `code/` **只作参考，不是基线**（完整工程已丢失）。可以拿来用的只有两块：

1. `frontend/src/components/PointCloudViewer.tsx` —— three.js 点云 + 第一人称漫游 + 自适应点大小
2. `frontend/src/lib/pointCloudParser.ts` —— 浏览器端 PLY 解析

其余（IOPaint 整包 445MB、SD 全家桶、GroundingDINO+SAM2、open3d 增强路径、6 个页面）全部不复用。

## v1 明确不跨过的三条线

1. **不和激光/卷尺比精度** —— 一旦需求变成"要能施工"，直接放弃，这个能力的上限就在这儿
2. **不引入第二个模型** —— v1 只有一个 DA3，显存预算全给它。任何"再加一个小模型"的诱惑都推到 v2
3. **不把编辑做成后端计算** —— 编辑在浏览器里发生，后端只存命令。这条一破，架构就会退化回旧项目那种纠缠状态

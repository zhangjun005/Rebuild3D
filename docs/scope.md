# 范围与主线：插画 → 点云 → 风格化渲染

<!-- @kron:intent product/scope-cuts -->

> 状态：已决策（2026-11）
> 影响：主线从「空间采集 / 户型」（[01](archive/01-product-v1.md)、[02](archive/02-direction-expansion.md) 的 A 方向）转为**插画点云风格渲染**。
> 前两份文档不废弃，归档在 `docs/archive/`，随时可回来。

---

## 1. 决策

```
一张插画
   │
   ├─► 深度估计（DA3 单图）
   ├─► 分层 + 补洞（背景延展 → 可选 LDI inpainting）
   ├─► 反投影成点云（+ 边缘剔除 + 重采样）
   └─► 风格化渲染（点画 / 描边 / 抖动 / 沸腾线）
            └─► 可交互网页 + 循环 GIF/WebM
```

**产出不是"模型"，是"一个能动的、有画风的东西"。** 这决定了它的目标是**好看**，不是**准确**。

---

## 2. 为什么这个转向是合理的（不是逃避）

| 理由 | 说明 |
|---|---|
| **验证成本低** ⭐ | A 方向的 go/no-go 关卡在第 4 步（俯视投影能不能看出户型），要搭 3 天才有答案。这条**第一天就能看到结果**，最坏情况一个下午就知道行不行 |
| **复用已有能力** | 深度估计这一层和 A 方向完全共用，转向不浪费 |
| **输出可传播** | 循环动图能发出去。A 方向的"房间 12.3 平米"没人转 |
| **不需要第二份精度论证** | 美术不需要米制、不需要和卷尺比。所有"精度焦虑"在这条线上不存在 |
| **表达自由度高** | 插画本身就是"不真实"的，深度模型的 OOD 问题在这里不是 bug，是"可控的失真" |

**必须同时记下的代价**（不粉饰）：

| 代价 | 说明 |
|---|---|
| **没有下游，也没有商业** | 产出是"好看的动图"，不是可用的模型。不构成生意 |
| **OOD 是唯一真风险** | 深度模型训练在真实照片上，插画是分布外。可能出现"整张纸片"的失败 |
| **只验证了"渲染"，没验证"空间"** | 之前积累的"多视图 / 米制 / 户型"判断力，这条线上用不到 |

**结论：把它定位成"技术基座 + 表达工具"，不是产品。** 这也和最初"想获得一些思考"的诉求一致。

## 3. 技术方案

### 3.1 五个环节

| # | 环节 | 技术 | 8GB | 状态 |
|---|---|---|---|---|
| 1 | 深度估计 | DA3 单图（见 3.2） | ✅ 单图最轻 | 待验证 |
| 2 | 分层 / 补洞 | 背景延展（零模型）→ 可选 LDI inpainting | ✅ | 待设计 |
| 3 | 点云生成 | 反投影 + 边缘断裂剔除 + 重采样 | ✅ | 待实现 |
| 4 | 风格渲染 | three.js shader（见 [渲染风格清单](rendering-styles.md)） | ✅ 零模型 | **可先做** |
| 5 | 导出 | GIF（Go `image/gif` 标准库）/ WebM / PLY | ✅ | 待实现 |

### 3.2 深度模型选型

**单图场景下，DA3 主系列（SMALL/BASE）的多视图优势用不上**，应优先考虑专门的单目模型：

| 模型 | 参数 | 许可证 | 特点 | 适配度 |
|---|---|---|---|---|
| `DA3-SMALL` | 0.08B | Apache-2.0 | 最轻，主系列单图退化 | 备选（最省） |
| `DA3-BASE` | 0.12B | Apache-2.0 | 主系列单图退化 | 备选 |
| `DA3MONO-LARGE` | 0.35B | **Apache-2.0** | **专门做单目相对深度**，直接预测 depth 而非 disparity | **首选** |
| `DA3METRIC-LARGE` | 0.35B | Apache-2.0 | 米制 + **天空分割** | 备选：天空分割可用来切背景 |

**注意**：插画不需要米制（反正是美术），所以 `DA3METRIC` 的唯一价值是它的 **sky seg**——正好能用来把背景抠出来，服务环节 2。值得单独测一次。

**待验证**（不能假设）：这些模型的 `Prediction` 是否带 `conf` 置信度图。官方文档写的是 *"conf ... optional, depends on model"*。如果首选模型没有 conf，就用"深度边缘梯度"代替过滤依据。

### 3.3 四个关键设计决策

**① 焦距当作艺术参数，不是相机参数**

插画没有真实相机。反投影需要一个焦距——**这可以是一个风格滑杆，不是标定值**：
- 焦距小（广角）→ 点云"厚"，空间拉伸感强
- 焦距大（长焦）→ 点云"薄"，接近浮雕/层叠

这是插画线相对真实重建的一个**优势**：不用纠结对不对，只要好看。

**② 正交 vs 透视，给一个开关**

插画（尤其日式、扁平风）常给人**正交投影**的观感。硬套透视会出"假透视"。两个都实现，让用户选——成本很低（反投影那一行不一样）。

**③ 补洞分两级，先做不需要模型的**

| 级别 | 做法 | 需要模型 | 效果 | 成本 |
|---|---|---|---|---|
| **L1** | **背景延展**：背景区域用边界外推/镜像，再整体推远 → 转动时背景是平滑渐变色 | ❌ | 够用，且不会失败 | 1 天 |
| **L2** | **LDI 补洞**：分层深度 + inpainting 补出被遮挡区域 | ⚠️ LaMa 级（~200MB，CPU 可跑） | 相机能转更大角度，看到侧面 | 2~3 天 |

**先做 L1。** 理由：L1 的成功率接近 100%，而 L2 在插画上的效果未知（Shih et al. 的 LDI 是在真实照片上训练的）。先用 L1 把"能动、好看"这件事做实，再决定要不要上 L2。

> **L2 的一个乐观点**：插画往往本身就有明显的平面分层（人物 / 中景 / 背景），**可能比照片更容易分层**。这是值得一试的理由。

**④ 点密度是风格参数，不是质量指标**

见 [渲染风格清单](rendering-styles.md)。点云独有的特权：**用密度表达明暗**。所以"点数"在这里是要主动控制的美术量，不是要最大化的性能指标。

## 4. 分阶段（按"能多快看到东西"排序）

| 阶段 | 内容 | 依赖 | 估时 |
|---|---|---|---|
| **P0** ⭐ | **渲染器原型 + 假深度**：three.js 风格化点云，深度先用占位（亮度/径向渐变） | **零依赖** | 半天 |
| P1 | 接真深度：装 DA3 sidecar，插画 → depth | conda env + 模型下载 | 1 天 |
| P2 | 点云生成：反投影 + 边缘剔除 + 重采样 + 正交/透视开关 | P1 | 1 天 |
| P3 | 风格层完整：点画密度 + 描边 + posterize + blue noise | P0 | 1~2 天 |
| P4 | 背景延展（补洞 L1）+ 沸腾线 | P2 | 1 天 |
| P5 | 导出循环 GIF / WebM | P4 | 0.5 天 |
| P6（可选） | LDI inpainting 补洞（L2） | P5 | 2~3 天 |

**P0 是关键设计**：把"渲染"和"深度"彻底分开。渲染器只需要一张深度图，所以**在任何模型装好之前就能做完并看到效果**。

## 5. 验证顺序：一个下午该验证什么

按"失败代价从大到小"排：

| 优先 | 验证 | 怎么验证 | 失败意味着 |
|---|---|---|---|
| **1** | **插画能不能出可用深度** | 拿 3 张风格差异大的插画（日式平涂 / 厚涂 / 线稿）跑一遍，肉眼看 | **整个方向要改**：退回纯 2.5D 分层视差，不做几何点云 |
| 2 | 渲染层观感对不对 | P0 假深度就能看 | 换风格组合，成本很低 |
| 3 | 转动穿帮有多严重 | P4 背景延展后转一圈 | 上 L2 补洞，或限制相机角度 |
| 4 | 动图传播效果 | 导出一个 GIF | 无关技术，只影响做不做下去 |

**第 1 条必须最先做**，而且必须在装完环境后立刻做——不要先花三天搭架构。

## 6. 交付物

| 交付物 | 说明 | 优先级 |
|---|---|---|
| **可交互网页** | 拖插画进去 → 立刻看到风格化点云，鼠标能转 | P0 核心 |
| **循环 GIF / WebM** | 自动绕圈一段，无缝循环 | 传播用，高 |
| PLY | 原始点云，给别的工具 | 低 |
| 风格预设 | "点画 / 版画 / 漫画 / 油画 / 像素"几套 shader 参数 | 提高可玩性 |

## 7. Go 在这条线上的位置

和之前判断一致，只是内容变了：

| 环节 | 语言 | 说明 |
|---|---|---|
| HTTP / 任务 / 文件管理 | **Go** | 单二进制 |
| 点云几何（反投影 / 剔除 / 重采样） | **Go** | gonum 够用 |
| **GIF / WebM 导出** | **Go** | `image/gif` 是标准库；WebM 调 ffmpeg |
| 深度推理 | Python sidecar | 约 300 行 |
| **风格渲染** | **TypeScript / shader** | 必须在浏览器侧 |

Go 依然占了服务 + 几何 + 导出三块，Python 只剩推理。

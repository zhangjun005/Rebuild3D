## 实测（2026-11-01）

同一张插画（4000×4000）、同一份 400k 点云配置、同渲染参数，只改 `process_res`：

| | res 504（原默认） | res 1008 |
|---|---|---|
| **主体边缘** | **撕裂成锯齿** | **顺滑连贯** |
| 背景 | 颗粒感重 | 干净 |
| 脸部 | 糊 | 可辨 |
| 推理 | 462 ms | 904 ms（约 2×） |
| 几何 | 405 ms | 592 ms |
| 峰值显存 | 2160 MiB | **3027 MiB**（8GB 够） |
| ILC1（400k 点） | 5.72 MB | 5.72 MB（不变） |

## 根因

```
遮挡边界在 504² 深度图上只有 1~2 像素宽
→ 边界像素的深度混了两个层（前景+背景平均）
→ 反投影后这些点位置错乱
→ 渲染出来就是撕裂的锯齿
```

提到 1008 后边界有 2~4 像素过渡，锯齿基本消失。

## 重要：这不违背 `depth-semantics-resolution-independent`

那条假设说的是**深度语义**（主体内结构 sub_iqr）与分辨率基本无关——涨 7.1 倍只改善 5~19%。
本条说的是**遮挡边界的空间精度**，它确实随分辨率线性改善。

两者不矛盾：
- 想要「主体内部的几何细节」→ 提分辨率没用，是模型上限
- 想要「轮廓/遮挡关系干净」→ 提分辨率有效，因为那是空间采样问题

## 代价与档位

| process_res | 推理 | 峰值显存 | 取舍 |
|---|---|---|---|
| 504 | 0.9 s | 2160 MiB | 边缘撕裂 |
| **1008（新默认）** | 2.2 s | 3027 MiB | **边缘顺滑，最佳平衡** |
| 1344 | 3.7 s | 3919 MiB | 更细但太慢 |

## 什么时候这条会破

如果换用**有真实几何结构**的输入（照片、3D 渲染图），遮挡边界的混层问题会轻一些，
提分辨率的收益主要体现在真实细节而非边界，量化对比需要重做。

# 点数预算：显存不吃点数，点数吃体积

> 用户希望靠**加点数**改善脸部细节。这个判断成立，但要把两个上限分清楚。

## 核心结论：显存瓶颈是 `process_res`，不是 `max_points`

```
显存 = 模型权重(1276 MiB) + 推理激活值
推理激活值 ∝ process_res²      ← 只和深度分辨率有关
点云生成在 Go（CPU）侧，不占 GPU 显存
```

**实测证据**：400k 点和 1M 点在 `process_res=1008` 下的推理显存**完全一样**（都是 3027 MiB）。

## 8GB 显存实测极限

| process_res | 深度像素 | 推理耗时 | 峰值显存 | 可用性 |
|---|---|---|---|---|
| 504 | 254,016 | 0.91 s | 2,160 MiB | 原默认（边缘撕裂） |
| **1008** | 1,016,064 | 2.25 s | 3,027 MiB | **现默认** |
| 1344 | 1,806,336 | 3.72 s | 3,919 MiB | 可用，偏慢 |
| 1792 | 3,211,264 | 10.99 s | 5,519 MiB | 太慢 |
| **2240** | 5,017,600 | 13.59 s | **7,577 MiB** | **8GB 真极限**（剩 611 MiB） |
| 2688 | 7,225,344 | 19.60 s | **10,090 MiB** | ❌ 超限，溢出到系统 RAM |

**结论：显存极限 ≈ `process_res 2240`；实用上限 1344；推荐 1008。**

## 点数的真实约束

| 约束 | 上限 | 说明 |
|---|---|---|
| `work_res` 候选网格 | **4096² = 16.7M** | 点数不能超过候选数 |
| `max_points` 硬上限 | **5,000,000** | `MaxMaxPoints` 常量，可放开 |
| ILC1 体积 | 见下表 | HTTP 传输 + 浏览器内存 |
| 浏览器渲染 | 未实测 | 4M 以内预计可行 |

### ILC1 体积（精确公式 `8 + 15n`）

| 点数 | ILC1 |
|---|---|
| 400,000 | 6.00 MB |
| 1,000,000 | 15.00 MB |
| 2,000,000 | 30.00 MB |
| 4,000,000 | 60.00 MB |
| 5,000,000（当前硬上限） | 75.00 MB |
| 16,000,000（= 4000² 全图像素） | **240.00 MB（228.9 MiB）** |
| 16,777,216（work_res 4096²） | 251.66 MB |

**输出的 PNG 并不随点数变大**：实测 400k / 1M 点的 1325×900 渲染图都是 ~1.5 MB
（PNG 压缩掉了点噪声的差异）。所以"点数↑ → 图片文件↑"只发生在 **ILC1 中间产物**，不在最终成品。

## 为什么加点数能改善脸部

颜色取自原图（4000px），而深度上限是 1008²。**点数可以远多于深度像素**——
多出来的点是同一几何表面上的**更密的颜色采样**，所以颜色细节会变细，几何不会。

脸部（约 600×600 px，占全图 2.25%）在不同点数下大约拿到：

| max_points | 脸上点数 | 等效分辨率 |
|---|---|---|
| 400k | ~9,000 | 95×95 |
| 1M | ~22,500 | 150×150 |
| 2M | ~45,000 | 212×212 |
| 4M | ~90,000 | 300×300 |
| 16M | ~360,000 | 600×600（全分辨率） |

**所以脸糊的本质是「颜色采样点太少」，不是深度不够。**

## 不采用「按区域加权采样」的理由

用户判断：风格化场景很难找到通用的加权公式，而且公式一旦失效会产生
"脸被过度采样、身体被欠采样"的新问题。**采纳这个判断，用加点数这条单调路径。**
